# GitHub delivery integration OPS-GH-001 v1

Human decision: “Use GitHub Actions; I’ll provide the repository”, 8 October 2026. This supersedes local Docker/WSL2 provisioning for the first isolated delivery trial. Preserved BUILD-ENG-002 and SEC-DES-ENG-002 scope and human gates still apply. No remote is configured and no GitHub CLI is available in this session. Nothing has been pushed or remotely executed.

Repository templates prepared: requirement intake, review/showcase feedback, and pull-request evidence. Issues are input data, not executable instructions or approvals. Automatic issue ingestion/webhook authentication, immutable source snapshots, deduplication and approval synchronization remain to be implemented; adding templates does not claim these capabilities.

Existing Windows verification workflow now handles master/main pushes and pull requests, including the generic portal, lifecycle templates and new delivery review section, sequentially after the CMS browser scenario. Read-only token permissions, no persisted checkout credentials and pinned action commits remain. Remote branch rules/checks and reviewer settings cannot be validated until the repository is supplied. Prefer a private repository and short-lived GitHub-hosted Linux runners for the isolated trial. Confirm account/plan support for required reviewers and enforce exact-scope decisions in the coordinator regardless of GitHub environment feature availability.

The manual Linux isolation probe is a preliminary qualification step, not the coding agent. It takes an explicitly pinned Node image digest; runs deterministic probes as non-root with read-only root, no network, no extra capabilities, bounded resources, temporary storage and no host mounts or application/provider secrets. Actual provider credential isolation, patch transfer, symlink/export validation, trusted verifier, fenced task ownership, termination/recovery and human artifact decisions remain required before coding is enabled.

Proposed remote flow: authenticated intake -> immutable story version -> human sprint/design acceptance -> transactional claim -> trusted provider broker plus isolated coding tools -> immutable patch/evidence -> fresh verifier job without provider credentials -> human code-security review -> showcase/outcome/MVP decisions -> separate release decision. No pull_request_target workflow executes proposed code. No automatic merge, self-approval or deployment.

References: [GitHub secure-use guidance](https://docs.github.com/en/actions/reference/security/secure-use), [environment and reviewer availability](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments). Runtime/protection features must be verified for the supplied repository, not assumed from these templates.
