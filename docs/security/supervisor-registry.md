# Supervisor registry checkpoint

10 October 2026, Australia/Sydney. AI-prepared code-security review; human acceptance pending. Synthetic-only, execution disabled.

The SQL coordinator no longer takes a caller-selected `SupervisorPolicy` at challenge issuance or evidence receipt. Trusted operator configuration must construct a `SupervisorRegistry` with a synchronous current-snapshot provider. The provider supplies an independently retained catalog digest, exact revision and Ed25519 root public key, plus the signed catalog document. There is no default root, environment-key fallback, sender-selected catalog/root, built-in URL fetch, registry edit route or production key generated by this change. Tests alone generate ephemeral registry-root and supervisor signing keys.

Catalog text is capped at 32768 UTF-8 bytes before parsing. Exact catalog shape, version/disabled flags, a positive anchored revision, issue/expiry window of at most 24 hours and independently expected canonical digest are required. The root signature covers domain `ai-sdlc/supervisor-registry/v1\n` followed by the canonical catalog SHA-256. Its signature is canonical 64-byte Ed25519 base64. The [Node crypto API](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptocreatepublickeykey) is used to import public SPKI DER keys, require Ed25519 and verify signatures. Every entry must have a canonical public-key encoding, bounded identifiers, exact verifier/qualification/image policy and validity interval contained within the catalog. At most 32 entries are allowed, sorted uniquely by supervisor/key ID. Each supervisor can have at most one active entry; revoked entries cannot resolve. Unknown supervisors, inactive/expired keys, ambiguous active registrations, malformed documents and unavailable providers fail closed.

Every coordinator issuance/receipt resolves the registry after task/story/challenge lock waits, using current PostgreSQL wall clock. The selected supervisor/verifier/qualification/image must match the retained task binding. New challenges are version 2 and include registry digest/revision as well as the key fingerprint; their expiry is capped by the selected registration's expiry. Version 1 challenges without registry metadata reject; no historical row is automatically trusted or upgraded. Claim format/signing bytes remain unchanged because the signed challenge digest binds the extended record. Existing synthetic v1 evidence can remain historical data; it cannot pass the new challenge validator.

Receipt requires a current anchored registry revision at least as new as the issued challenge. The same revision must retain the same digest. A newer catalog can preserve a still-active identical key/policy without invalidating outstanding challenges; revocation, key rotation, expiry or policy replacement denies receipt. The final consume SQL also checks registration expiry against database wall clock. Invalid registry evidence never consumes a nonce or inserts an evidence event. The lower-level cryptographic helper still takes an explicit policy for offline integrity checks; it cannot write the task ledger or establish current registry authorization.

The latest-anchor provider is a trust boundary, not an implemented external service. It must be wired only by trusted operator code, independently of candidate/model data and application-database rollback. A process-local high-water latch remembers fully authenticated catalogs, including ones that deny a revoked/expired key, and denies older revisions or a different digest at the same revision. That latch does not survive process loss. Returning an old catalog together with an old anchor can defeat revocation after restart; a signed document alone supplies no latest-revision proof. Tests cover the in-process latch and old-document rejection against a current independently retained anchor, not an external non-rollback guarantee. The provider is read synchronously at authorization time; registry revocation and the PostgreSQL commit are not a distributed atomic operation. A future service must define authorization leases/linearization, operational root/key rotation, independent key custody and transport authentication before execution can be attached.

Tests cover signed active lookup, immediate revocation/re-registration, old document/current anchor mismatch, wrong/private root, signature tamper/domain substitution, catalog/key expiry, malformed/oversized input, duplicate/ambiguous entries and array-shaped hash coercion. Database scenarios cover anchored issuance, revocation between issuance and receipt, old-catalog replay and revocation during an actual row-lock wait, preserving nonce/event state on denial. Prior signature, transactional rollback, replay, exact-byte persistence, access and fresh-process authentication checks remain in place. All approval gates and keys are synthetic test fixtures, never human acceptance or deployed identity.

The first uncommitted typecheck found a constructor definite-assignment error; a direct throwing guard fixed it. That pre-final log is retained and does not represent the final source. No schema collection change or production key migration was needed. The installed Next.js data-security guide was read before internal server-code edits. Accepted planning/design documents were not edited.

Execution, execution retries and promotion remain disabled; existing administrator recovery of reservations with no launched child is unchanged. External durable evidence/journal/replay authority, independent supervisor signing/key registration, qualification freshness/verdict semantics, database restore and supervisor/job/observer/host/daemon-loss recovery remain unqualified. This registry must not be used as process-termination proof or automatic retry authority. No paid model calls, real taskboard work, merge or deployment occurred.
