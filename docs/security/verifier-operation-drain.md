# Qualification of pending Docker operations

9 October 2026, Australia/Sydney. AI-prepared code-security checkpoint; human acceptance pending. Continues NB-003/004 without changing the accepted plan or connecting task execution.

An empty container inventory does not prove safety while another client can still create or start the recorded container. The new qualification-only recovery guard requires the trusted observer to confirm controller closure, Docker-client closure and proxy closure before it queries the daemon or removes anything. Missing or false proof denies recovery. The proof is a caller assertion from trusted qualification code, not signed evidence or a production identity mechanism. The earlier low-level reconciler remains an internal primitive for completed-operation probes; it must not be used alone for running tasks.

A private Unix-socket proxy pauses the actual Docker CLI's create/start operation before forwarding its request or after receiving the daemon's successful response. Four cases kill/cancel a separate requesting controller while that CLI is still pending. The surviving observer first verifies premature recovery is denied, then intentionally releases the delayed operation, waits for the client `close` event, closes the proxy and waits for backend handlers to settle. Only then may owner/name/ID reconciliation remove the container. Request-delay create must show an empty inventory at controller death followed by a real late creation. Both start cases must show a live parent/child/grandchild tree after controller death before removal. Create cases use SIGKILL; start cases use SIGTERM. Retry authority always remains false.

The proxy is a test fault injector, not a deployable model broker. Its socket is inside a newly created private host temporary directory and is never mounted into a candidate container. It allows handshake endpoints and the selected create/start endpoint only, bounds request/response bodies and backend time, and connects exclusively to the local Docker Unix socket. Generated code has no host mounts, network, credentials or Docker socket. Trusted Docker CLI arguments choose the pinned image and existing nonroot/read-only/resource controls. No raw HTTP body, Docker diagnostics or candidate stdout enters evidence annotations.

Durable intent is fsynced before the operation; no task approval or lease transition is recorded. The surviving observer owns the direct Docker client process and the proxy, so it can await their closures. A blocked/failed proxy backend prevents confirmation. Whole-job cancellation, death of that observer/proxy host, daemon restart, loss of trusted identity/journals and all remote-daemon behavior remain unqualified. The pauses occur at controlled transport boundaries, not every possible internal daemon instruction. This proves the late-effect hazard and a drain-before-reconcile policy in the selected CI environment, not universal crash recovery.

Local orchestration tests cover missing/false drain proof before any daemon query, absence, foreign ownership and daemon/removal/survivor failures. Physical scenarios run only in disposable Linux CI. No taskboard feature, coding model, provider purchase, execution enablement, retry, merge or deployment is introduced.
