# Task artifact binding checkpoint

9 October 2026, Australia/Sydney. AI-prepared code-security review; human acceptance pending. Partial NB-002/003/004 continuation of the accepted BUILD-ENG-002 scope. Execution remains disabled.

An internal SQL coordinator can now bind a currently reserved attempt to exact approved source, candidate, check-policy bytes, verifier bytes, pinned image, qualification-evidence reference and supervisor identifier. The record also includes project, immutable story revision/scope, owner, fence, attempt and both exact human gate IDs/actors/decision keys. It generates a separate random recovery lookup ID. The lookup ID and supervisor name are public identifiers, not credentials, authenticated service identity or permission to recover a task.

Binding uses the existing story advisory lock and task row lock. It revalidates current project/story integrity, latest revision, human sprint/design gates, exact reservation and database wall-clock lease/deadline after lock waits. The insert itself repeats reservation/time predicates. Existing identical calls are idempotent; a different candidate or verifier cannot replace the same attempt's binding. One event and one binding are committed atomically. A fresh coordinator process can reload the receipt from PostgreSQL using an independently retained expected binding hash. Re-reading checks current eligibility again; a stale owner/fence/attempt, expired lease, superseded story, changed gate authority or corrupted row fails closed.

The narrow source-capsule format remains unchanged. Approved source must match the story's source hash. Candidate and base must contain the same selected paths; changes are limited to the story's explicit allowed paths, preserving protected dependency bytes. Adding/deleting files is unsupported in this checkpoint. Check policy is hashed from bounded supplied bytes and must match the story. Verifier bytes are bounded and hashed separately. Only the previously tested pinned Node image is accepted. Candidate integrity does not imply approval, behavioral correctness, provenance, code-security review or execution permission.

The new admin-readable binding collection denies API creation/update/deletion. Hooks also deny writes through Local API access overrides; the SQL coordinator is the only application writer. Privileged database access can still rewrite/delete rows, so this is application immutability rather than tamper-proof storage. An independently retained receipt hash detects row changes at inspection; a hash fetched solely from the same compromised row is insufficient. No raw source, candidate, verifier/check bytes, private keys or credentials are stored in the binding collection.

Trusted verifier material must come from coordinator/operator code, never from candidate-selected checks. Recording its hash, supervisor name or qualification reference does not establish that the supplied verifier or independent service is trustworthy. This component binds exact values; independent supervisor authentication, qualification freshness/policy, durable external evidence and host-loss recovery remain outstanding. The record has `executionAllowed:false` and `syntheticOnly:true`; validation returns `retryAuthorized:false`. No worker, provider, launch endpoint, execution transition or promotion path consumes it yet. Existing reservation-only recovery remains valid only while no child can be launched.

Tests cover source/check mismatch, protected dependencies, path additions/deletions, oversized verifier material, forged execution flags, changed candidate/verifier/image/identifiers, concurrent idempotent binding, conflict denial, API write/read restrictions, fresh-process reload, privileged-row tamper, gate-authority change, stale attempts, expiry during row-lock wait and supersession. Synthetic test gates are removed after the suite and do not constitute human approval. Production database migrations/backups, independent recovery identity, whole-job cancellation and operations qualification are incomplete.

The installed Next.js data-security guide was read before the change. Coordinator functions remain internal trusted server code; no Server Action or route was added. Existing source-capsule transport limits still apply: callers must bound external JSON before parsing, and only synthetic reviewed input is permitted.
