# Verifier resource and cancellation checkpoint

9 October 2026, Australia/Sydney. AI-prepared review, human code-security acceptance pending. Continues NB-003/004 without changing accepted scope or enabling task execution.

The existing trusted controller now inspects Docker's memory, combined memory/swap, PID, CPU, network and read-only-root settings before each candidate starts. New probes test a touched-memory allocation beyond the 128 MiB ceiling (requires daemon-observed OOM termination), temporary-storage exhaustion (requires ENOSPC), and process exhaustion (requires EAGAIN after some successful child starts). Positive resource probes return the same three controller-owned expected values; a generic startup failure cannot satisfy them. PID probe children are killed and reaped by the probe, and the outer controller still removes and checks the entire container.

Cancellation is tested by aborting the attached Docker client while a candidate with a child/grandchild process is pending. Passing requires an actual AbortError, daemon evidence that the container started, and confirmed named-container removal before the next case. This tests client-operation cancellation handled by a surviving controller. It does not qualify controller death, CI-job cancellation, daemon restart or an external recovery worker. These remain required before execution ownership can safely retry.

A readable, randomly named synthetic host canary file is created outside every mounted source directory. Known probe code attempts its absolute path and the same path through `/proc/1/root`; both must return ENOENT. Container PID 1's environment must omit the controller's synthetic canary variable. The host checks the canary's contents before and after the suite. Evidence retains its digest, never its contents. Canary and source staging remain in disposable runner temporary storage until runner disposal. No real credentials are introduced or read.

Eighteen variants run three cases each: 54 container executions and 162 capsule tamper denials on a fully passing path. The prior 13 variants remain. No actual provider/model calls, generated taskboard feature, task approval or ownership transition is performed. Resource limits depend on the selected runner/kernel; these probes qualify only the observed configuration. Arbitrary hostile code, side channels and kernel vulnerabilities are not exhaustively tested. Runtime evidence must pass before reporting this checkpoint as qualified.

References: [Docker resource controls and equal memory/swap semantics](https://docs.docker.com/engine/containers/resource_constraints/), [attached container start](https://docs.docker.com/reference/cli/docker/container/start/), and [Node child-process cancellation](https://nodejs.org/api/child_process.html).
