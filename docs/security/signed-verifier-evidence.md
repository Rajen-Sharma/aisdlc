# Signed verifier evidence protocol

10 October 2026, Australia/Sydney. AI-prepared implementation review; human acceptance pending. Synthetic-only, execution disabled.

## Trust boundary

The internal coordinator accepts an operator-selected `SupervisorPolicy`: an Ed25519 public `KeyObject`, key ID, supervisor ID, verifier hash, qualification hash and pinned image. There is no default key, sender-selected key, environment credential, signing endpoint or production key generated by this change. Only tests generate ephemeral private keys. Before a real supervisor is deployed, its private key must be held outside candidate containers, workspaces and model tools; independent registration, rotation/revocation, transport authentication and service operations must be established. A caller that trusts an attacker-selected public key defeats this boundary.

The implementation authenticates a signature against that explicitly trusted key. It does not prove that the key is held by an independently operated service, that a qualification reference is valid/current, or that the signed verdict is truthful. There is no `verified` state or human artifact-review bypass. The task remains `awaiting-verification`, with its existing binding digest unchanged, even for a signed `pass`. Existing human artifact gates remain unavailable pending the complete verified artifact ledger.

## Challenge and signed statement

An awaiting-verification candidate must still match the current project, latest story, exact sprint/design gates and independently retained binding hash. Its completed attempt/fence and null owner must match the bound attempt. Current supervisor/verifier/qualification/image policy must match the binding. The coordinator issues one random UUID challenge per binding, valid for at most 300 seconds by PostgreSQL wall clock. It binds the exact binding digest, supervisor/key ID, SHA-256 fingerprint of the public SPKI DER key, verifier and qualification hashes, image, issue/expiry seconds and synthetic-only/disabled-execution flags. The caller must retain the challenge digest independently of the database row. Expired challenges cannot renew automatically.

The signed claim has exactly version, challenge hash, evidence SHA-256, byte length, claimed verdict (`pass`, `fail` or `error`), `syntheticOnly:true` and `executionAllowed:false`. Its signing bytes are UTF-8 `ai-sdlc/verifier-result/v1\n` followed by the canonical JSON SHA-256 of that claim. This domain separates other signing protocols and tolerates JSONB key ordering. The Ed25519 signature must be canonical base64 encoding of exactly 64 bytes. Node's [crypto.verify documentation](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptoverifyalgorithm-data-key-signature) describes the API used; the implementation requires an Ed25519 public key and passes `null` as its algorithm.

Envelope text is bounded to 4096 UTF-8 bytes before parsing; evidence is bounded to 1–65536 bytes, copied before waiting for locks, and its exact bytes/length must match the signature. External transports must bound streams before allocation or calling this API. Evidence is inert data: it is never executed or parsed for tool instructions. No arbitrary raw evidence or private key is printed in diagnostics. Signatures are checked against the current trusted policy again at receipt, denying substituted/revoked keys when the trusted caller supplies the updated policy.

## Atomic receipt and durable storage

Receipt takes the shared story advisory lock, task row lock and challenge row lock. It rechecks candidate/binding/gates and challenge digest/context, then reads database wall clock after lock waits. Signature or byte mismatch leaves the challenge issued and writes nothing. The final consume update repeats expiry against `clock_timestamp()`. Consumption, immutable evidence insert and event commit in one transaction; unique binding/challenge/result constraints and task serialization permit one winner. Replay, concurrent losing submissions and conflicting second results reject. No automatic task retry or challenge renewal follows denial.

The signed envelope and exact bounded evidence bytes (base64) are retained in PostgreSQL, not merely an external URL or hash. A fresh production-mode coordinator process can reload and cryptographically recheck the stored bytes with the retained challenge and trusted public key. Admin-only collections reject API and Local API override writes/deletes; only internal SQL writes. This is application immutability, not tamper-proof storage. Privileged SQL can delete/rewrite rows, including replay state; retained independent digests and signatures are essential, and a rollback/deletion threat needs an external append-only authority. PostgreSQL backup/restore and host-loss durability have not been qualified. No external artifact/object-store provider is selected or provisioned.

## Validation and remaining work

Tests cover valid pass/fail/error signatures without acceptance, JSON key reordering, wrong keys/IDs/verifier/qualification/image, private-key misuse, wrong challenge, future/expired/non-integer clocks, replaced bytes, changed claim/signature, cross-protocol signatures, malformed/oversized input and forged execution flags. Database scenarios cover gate-authority changes, binding corruption, unchanged state after rejection, expiry while waiting on a task lock, transaction rollback on an injected SQL-client fault after challenge consumption, concurrent exactly-once consumption, replay denial, API immutability and fresh-process retained-byte authentication. All test approvals and signed proof are synthetic; no verifier or candidate executes on Windows.

The next recovery qualification must preserve these distinctions:

| Failure | Required safe behavior | Current evidence |
| --- | --- | --- |
| Evidence insert fails after nonce consumption | Roll back consumption and all result/event writes | Injected SQL-client failure in a real transaction |

| Host/database storage disappears or restores an old snapshot | External durable receipt/replay authority must prevent lost-result acceptance or unsafe retry | Not qualified; local PostgreSQL rows are insufficient |

These are prerequisites for attaching a supervisor to execution, rather than implied permissions from a valid signature or an empty container inventory.
